## 1. 需求概述

### 1.1 问题背景

当前系统已有基于 numpy 向量化的回测引擎，该引擎：
- **优点**：性能快（1 年 1h 数据 < 10s），适合规则策略快速参数优化
- **缺点**：一次性全量计算，无法逐根 K 线调用 AI 进行市场分析与决策，不支持"AI 辅助决策"场景

本方案新增**逐根推演+AI 驱动**的回测模式，与现有向量化回测**完全独立并存**。

### 1.2 核心目标

1. **逐根推进**：从开始时间逐根 K 线推进，每次只看当前及历史数据，不提前看到未来
2. **AI 逐根分析**：每根 K 线触发 AI 分析，AI 根据当前市场状态给出交易决策
3. **完整记录**：每笔交易记录 AI 分析原文、交易计划、止盈止损、决策理由
4. **灵活范围**：支持"K 线数量"和"时间跨度"两种回测范围定义
5. **配置锁定**：回测开始后所有参数锁定，保证回测结果可复现

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **独立不侵入** | 不修改现有向量化回测，新增独立数据模型和代码路径 |
| **真实模拟** | 模拟真实交易节奏，每根 K 线只能看到到当前为止的数据 |
| **可追溯性** | 完整记录每笔交易的决策过程，便于复盘改进 |
| **渐进式交付** | MVP 阶段保证核心流程可用，后续逐步优化 |
| **错误容错** | AI 调用失败自动降级，不中断回测 |

### 1.4 策略前提规则（硬性约束）

所有策略在回测和实盘运行时，必须遵守以下三条默认前提规则。这些规则是**硬性约束**，不可被 AI 或用户操作绕过，但支持在策略编辑页中修改其开关状态。

| 规则 | 默认值 | 说明 | 实现方式 |
|------|--------|------|----------|
| **单仓规则** | `true`（开启） | 永远手里只开一个单子，只有当单子结束后（平仓），才可以考虑下一个单子 | 决策执行器中强制检查，持仓状态下忽略所有开仓信号 |
| **强制止损** | `true`（开启） | 每笔开仓必须设置止损价，AI 未提供止损时由系统自动计算 | 决策执行器在开仓时校验，未提供止损则按 `entry_price * (1 - 默认止损百分比)` 自动计算 |
| **严格执规** | `true`（开启） | AI 分析必须严格遵循策略规则，不允许偏离策略框架 | Prompt 中明确要求严格遵守策略入场/出场规则，AI 仅作为规则辅助决策 |

**前提规则存储结构（在 Strategy.rules.prerequisites 中）：**

```json
{
  "prerequisites": {
    "single_position": {
      "enabled": true,
      "description": "单仓规则：同时只持有一个仓位，平仓后才可开新仓"
    },
    "mandatory_stop_loss": {
      "enabled": true,
      "default_stop_loss_pct": 0.03,
      "description": "强制止损：每笔开仓必须设置止损价"
    },
    "strict_execution": {
      "enabled": true,
      "description": "严格执规：AI 决策必须遵循策略入场/出场规则"
    }
  }
}
```

**编辑入口：** 策略编辑页 → 规则编辑 → 前提规则 Tab/折叠面板，支持用户开启/关闭每一条规则，调整强制止损的默认百分比。

### 2.2 组件职责划分

| 组件 | 职责 | 说明 |
|------|------|------|
| `AIBacktestService` | 业务编排 | 验证配置、创建记录、触发任务 |
| `AIBacktestTask` | 异步执行 | Celery 异步任务，逐根推进主循环 |
| `AIMarketAnalyzer` | AI 分析封装 | 构建 Prompt、调用 LLM、解析 JSON 输出 |
| `DecisionExecutor` | 决策执行 | 根据 AI 决策执行开仓/平仓，计算盈亏 |
| `BacktestProgressPublisher` | 进度推送 | 通过 Redis Pub/Sub + SSE 推送给前端 |
| `AIBacktestSummary` | 结果统计 | 计算各项指标，生成总结报告 |

```python
class AIBacktestContext:

    timeframe: str
    start_time: datetime
    mode: str  # "kline_count" / "time_span"
    total_klines: int
    initial_capital: float
    fee_rate: float
    use_ai: bool

    # 预热数据
    preheat_klines: List[KlineItem]

    # 当前状态
    current_equity: float
    available_cash: float
    current_position: Optional[Position]
    completed_trades: List[AIBacktestTrade]
    current_kline_index: int
    total_trades: int
    ai_call_count: int
```

### 6.4 AI 失败兜底策略

| 失败场景 | 处理方式 |
|----------|----------|
| 单次调用超时 | 等待 30s 后重试 1 次 |
| 重试仍失败 | 跳过当前 K 线，不操作，记录"AI 调用失败" |
| 连续 3 次失败 | 打印警告日志，降级为纯规则引擎模式 |
| JSON 解析失败 | 提取有效部分，无法提取则跳过 |
| 决策参数不合理（如资金超限） | 风控校验拦截，跳过，记录"AI 决策被风控拦截" |

## 7. 异步任务与进度推送

### 7.1 异步执行：Celery Worker

- AI 回测作为 Celery 异步任务执行，不阻塞 HTTP 响应
- 任务 ID 与回测 ID 一一对应
- 并发限制：同一用户最多同时运行 3 个 AI 回测任务

### 7.2 进度推送：Redis Pub/Sub + SSE

```
Celery Worker 每推进一根 K 线 → 更新 DB → publish 进度到 Redis channel: ai-backtest-progress:{backtest_id}
                                 ↓
前端 EventSource 连接 GET /progress → 后端 subscribe Redis channel
                                 ↓
后端将 Redis 消息通过 SSE 转发给前端
                                 ↓
收到完成/错误消息 → 关闭 SSE 连接
```

**优点：**
- 前端无需轮询，实时性好
- 后端连接数轻量（一个回测一个连接）
- 利用现有 Redis 基础设施，无需新增基础设施

### 7.3 进度持久化

- 每推进 10 根 K 线更新一次 DB 进度
- SSE 推送每根 K线都推送
- 前端刷新页面可从 DB 恢复进度

```
用户前端
   │
   │  1. 提交回测配置
   ▼
后端 API
   │
   │  2. 参数校验（配置有效性、数据可用性）

   │

   │  6. 获取预热数据（start_time 前 300 根）
   │  7. 推送进度：stage=preheat, progress=5
   │  8. 预拉取回测区间全部 K 线到内存
   │  9. 初始化回测上下文（权益、持仓等）
   │
   │  开始逐根推进主循环
   │  ┌─────────────────────────────────┐
   │  │  for each kline in klines:
   │  │
   │  │  a. 更新进度到 DB + 推送 SSE
   │  │  b. 计算技术指标（MA/RSI/MACD 等）
   │  │  c. 构建 AI 输入 → 调用 AI 分析
   │  │  d. AI 返回决策 → 执行决策（开仓/平仓/持有）
   │  │  e. 记录交易（若有开平仓）
   │  │  f. 更新上下文状态
   │  │
   │  │  until 达到终止条件
   │  └─────────────────────────────────┘
   │
   │  10. 计算总结指标 → 更新 result_summary
   │  11. 更新 status → completed
   │  12. 推送进度：stage=done, progress=100
   ▼
前端
   │
   │  13. 收到 done 事件 → 关闭 SSE → 请求完整详情 → 渲染结果
   │
   └── 完成
```

## 10. 技术决策矩阵

### 10.1 异步任务选型

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Celery + Redis | 已有基础设施，直接复用 | 需要 Worker 进程 | ✅ 选用 |
| 后台线程 + HTTP 长轮询 | 无需额外 Worker | 扩展性差，不支持多实例 | ❌ 不选 |

### 10.2 进度推送选型

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Redis Pub/Sub + SSE | 实时性好，复用现有 Redis | 需要保持 HTTP 连接 | ✅ 选用 |
| 前端轮询（2s 一次） | 实现简单，兼容性好 | 延迟高，请求冗余 | 备选，若 SSE 有问题可降级 |

### 10.3 结果存储选型

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 独立新表 `ai_backtests` | 完全隔离，不影响现有 | 少量冗余存储 | ✅ 选用 |
| 复用现有 `backtests` 表 | 无冗余 | 需要加大量 nullable 字段，耦合高 | ❌ 不选 |

## 11. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| AI 调用 Token 消耗大 | 成本高 | 只传入最近 50 根 K 线，不传入全部历史；缓存相同分析结果（V1.1） |
| AI 调用延迟高 | 回测慢 | MVP 接受，后续批量分析优化 |
| Token 数量超限 | 调用失败 | 控制输入长度，超出截断；降级为规则引擎 |
| AI 输出格式不对 | 无法解析 | 重试 1 次，仍失败则跳过该根 |
| 用户同时启动太多回测 | Worker 耗尽 | 限制同一用户最多 3 个并发 |
| OOM（内存） | 任务崩溃 | 预拉取全部 K 线到内存，5000 根也只≈几 MB，问题不大 |
| 网络中断 | 用户看不到进度 | 进度持久化在 DB，刷新页面可恢复 |
